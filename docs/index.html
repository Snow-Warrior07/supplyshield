What the model assumes

Single plant, three product SKUs, whole units and whole yen, partial order fulfillment, a common seven-day deadline, and one day reserved for assembly/delivery. Normal and expedited modes share physical supplier-component capacity. Supplier qualification, prices and lead times are declared assumptions. Sales exposure is not profit or realized loss.

Implementation and solver evidence

The public website uses bounded enumeration in a background worker. The extensible Python app uses OR-Tools CP-SAT. FEASIBLE means an incumbent exists; OPTIMAL means the search proved the objective. Python daily planning and API deployment instructions are in the repository.

A FEW USEFUL ANSWERS

Before you act.

Does this use real supplier data?

No. The repository generates a fictional electronics supply chain with reproducible seeds. This website demonstrates a decision process; it does not identify or predict the reliability of real suppliers.

Why can the optimizer tie the greedy plan?

A heuristic can find the optimum in a particular case. The default outage is one such case. The optimizer searches feasible allocations and proves its status when it finishes; a tie is reported honestly.

What is priority fulfillment?

Each order has a declared priority weight. Priority fulfillment is the fraction of weighted demand fulfilled. Unit fill counts all units equally. The recovery model maximizes the weighted score first.

Where are saved scenarios stored?

Only in this browser's local storage. Saving stores the seven sample input settings; restoring recomputes the results. A shared URL contains those settings so another person can reproduce the scenario.

Can this place orders or connect to my ERP?

The website exports a plan for review. It does not execute a purchase. The Python API is available in the repository; a real integration needs approved data, access controls, and an operational pilot.
